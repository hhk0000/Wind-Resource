# 协作与版本管理

## 仓库与发布

代码仓库：hhk0000/Wind-Resource。main保存当前集成版本；gh-pages只保存GUI发布文件，不含原始上传资料。main中的gui/是网页唯一来源，请勿单独修改gh-pages。

当前基线：v0.1.0-prototype，对应方案V0.1和六页面GUI。方案快照分支：design/v0.1。Git标签留存批准的可回退版本，方案分支保存需比较的独立方向。不要以重复复制整个目录代替Git历史。

GitHub Pages配置为“Deploy from a branch”，选择gh-pages、/（root）。网页地址须以Pages实际返回值和部署检查为准；提交代码不代表网页已经上线。

## 后续共同开发

1. 用户描述修改对象、期望效果和应保留内容；普通页面细节可直接边改边验证。
2. 每轮变更先记录范围，检查现有改动；使用现有检出，不创建worktree。
3. 较大方案探索使用design/<名称>；实现使用feature/<名称>；修复使用fix/<名称>。已确认的小幅界面迭代可直接提交main。
4. 修改后运行与影响范围匹配的检查；涉及交互运行tests/smoke.py，记录通过及未完成项。
5. 按具体行为写提交信息，推送到仓库。用户明确要求保留的候选方案独立提交并打标签，不强制合并。
6. main中gui变更触发工作流更新gh-pages；浏览器等待Pages部署后刷新。页面右下方显示构建版本，便于确认是否更新。
7. 每个阶段成果更新CHANGELOG.md及方案台账；重要基线新增版本标签，标签一经发布不移动。

## 回退

先git fetch origin --tags。查看基线：git show v0.1.0-prototype；比较：git diff v0.1.0-prototype..main -- gui docs。

已共享main采用git revert撤销明确的变更提交，再推送新提交；不force-push、不reset远端。恢复某一历史方案应先开restore/<版本>分支，验证后合并。gh-pages更新使用普通推送；如果远端有意外差异，工作流失败并提示人工检查，不覆盖未知改动。

## 数据与凭据

上传样本仍仅在浏览器内存，本版本未实现云端资料归档。不得将真实测风原件、客户资料、规范全文、私钥、Token或.env提交Git；生产资料进入对象存储并按项目授权。新规范和模板的知识产权需确认。自动发布分支只包含gui/，不发布方案附件和测试数据。

## 自动发布前提

仓库需允许Actions运行且GITHUB_TOKEN有contents:write。工作流只负责将gui/同步到gh-pages，GitHub Pages本身需先启用。若仓库策略不允许自动推送，保留本地提交及失败记录，修复策略后重跑，不能声称已发布。
